# 통합 스키마 정의

번개장터 / 중고나라 / N플리마켓 / 11번가 네 플랫폼의 크롤링 결과를 하나의 형태로 합친 스키마다.
앞의 셋은 중고, 11번가는 새상품 비교 기준이다.
`crawler/unified/transform_to_unified_schema.py`가 이 문서의 규칙대로 변환하고,
`crawler/unified/validate_unified_schema.py`가 규칙을 지켰는지 검사한다.

**설계 원칙** — 값이 없는 자리에 임의의 `0`·`false`·추정값을 채우지 않는다.
판단이 불가능하면 `null` 또는 `UNKNOWN`으로 남긴다.

## 1. 필드 목록

| `platform_product_id` | str | 플랫폼 내 상품 ID |
| `url` | str | 상품 상세 페이지 주소 |

| `price_range` | object \| null | 옵션에 따라 가격이 달라질 때만 값이 있다 → [2장](#2-상품-가격-price) |
| `currency` | str | `KRW` |
| `description` | str \| null | 상품 설명. 전화번호·이메일은 마스킹됨 |
| `images` | str[] | 이미지 URL 목록 |
| `condition_level` | str | 상품 상태 6종 → [3장](#3-상품-상태-condition_level) |
| `condition_raw` | str \| null | 플랫폼 원본 상태값(문자열로 통일) |
| `trade_method` | str[] | `PARCEL` / `MEET` 조합 |
| `delivery_fee` | object | 배송비 → [4장](#4-배송비-delivery_fee) |
| `location` | object | 거래 위치 → [5장](#5-위치-location) |
| `collected_at` | str | 수집 시각(ISO 8601) |

**제외한 필드**

- `category_path` — 3사 카테고리 체계(1단/3단/가변)를 매핑할 시간이 부족해 이번 버전에서 완전히 제외
- `brand` — N플리마켓만 제공하는데 판매자 자유 입력이라 신뢰할 수 없다. 실제로 샤넬 가방 게시글의 `brandName`이 `"안"`으로 등록된 사례를 확인했다

### 플랫폼별 특성

**앞의 세 곳은 중고, 11번가는 새상품이다.** 구조가 달라 채워지는 필드도 다르다.
없는 값을 억지로 채우지 않으므로, 아래 `없음`은 오류가 아니라 그 플랫폼의 성질이다.

| | 번개장터 | 중고나라 | N플리마켓 | 11번가 |
| --- | --- | --- | --- | --- |
| 취급 | 중고 | 중고 | 중고 | **새상품**(중고 일부 포함) |
| `condition_level` | 5단계 | 3단계 | 4단계 | `NEW` / `USED` |
| `description` | 있음 | 있음 | 있음 | **없음** |
| 이미지 | 여러 장 | 여러 장 | 여러 장 | 평균 1.45장 |
| `trade_method` | 택배·직거래 | 택배·직거래 | 택배·직거래 | **택배만** |
| `location` | 있음 | 있음 | 있음 | **없음**(`NONE`) |
| `price_range` | 없음 | 없음 | 없음 | **옵션 상품만** |
| 편의점 택배 | 있음 | 있음 | 있음 | 없음 |
| 도서산간 배송비 | 없음 | 없음 | 있음 | 있음 |

읽을 때 주의할 점이 셋 있다.

**`description`과 이미지 개수로 상품을 평가하면 안 된다.** 11번가는 설명이
판매자가 올린 이미지라 우리가 텍스트로 읽지 못한다. 판매자가 성의가 없는 것이
아니라 수집이 불가능한 것이다. 이 값으로 점수를 매기면 새상품이 전부 밀린다.

**`location`이 `NONE`이라고 오류가 아니다.** 11번가는 직거래가 없어 만날 장소
자체가 없다. 중고 플랫폼도 택배 전용 글이면 똑같이 `NONE`이다. 그러므로 거리
계산은 플랫폼이 아니라 `location.precision`으로 분기해야 한다.

**`condition_level`은 중고 안에서만 변별력이 있다.** 11번가는 사실상 전부 `NEW`다.

11번가만의 수집 방식과 한계는 [8장](#8-11번가에서-따로-챙기는-것)에 모아 두었다.

## 2. 상품 가격 `price`

플랫폼 원본의 판매가를 그대로 담는다. **배송비는 포함하지 않는다.**

| 플랫폼 | 원본 경로 |
| --- | --- |
| 번개장터 | `common.price` |
| 중고나라 | `common.price` (JSON-LD `offers.price`) |
| N플리마켓 | `common.price` |
| 11번가 | `common.price` (검색 `finalPrc`). **옵션 상품이면 최저가** → [`price_range`](#옵션에-따라-달라지는-가격-price_range) |

### 실제 데이터 (표본 40건)

| 상품군 | 최저 | 최고 |
| --- | --- | --- |
| 무료나눔 | **0원** | 20,000원 |
| 문화상품권 | 2,000원 | 11,111,111원 |
| 닌텐도 스위치 OLED | 34,000원 | 360,000원 |
| 냉장고 | 150,000원 | 900,000원 |
| 샤넬 가방 | 60,000원 | 4,300,000원 |

**`price: 0`은 정상값이다.** 무료나눔 게시글에서 실제로 3건 확인됐다.

> ⚠️ **이상치 주의** — `11,111,111원`은 `"문화상품권 개진상 악질 닉네임HH"`라는 저격 게시글이다.
> 판매 의사가 없는 더미 가격이며 크롤러 필터를 통과한다.
> 상품이 아닌 게시글 판별은 에이전트 Tool/프롬프트 단계에서 처리하기로 했다.

### 옵션에 따라 달라지는 가격 `price_range`

11번가 검색 결과의 가격은 **옵션 중 가장 싼 값**이다. 그대로 쓰면 새상품이
실제보다 싸 보이고, 중고와 비교할 때 한쪽으로 기운다.

```jsonc
{
  "price": 26420,
  "price_range": { "min": 26420, "max": 30950, "option_count": 4 }
}
```

| 필드 | 타입 | 설명 |
| --- | --- | --- |
| `min` | int | 옵션 중 최저가. `price`와 항상 같다 |
| `max` | int | 옵션 중 최고가 |
| `option_count` | int \| null | 가격을 확인한 옵션 수(품절 제외) |

| 조건 | `price_range` |
| --- | --- |
| 옵션에 따라 가격이 다름 | `{min, max, option_count}` |
| 옵션은 있으나 전부 같은 가격 | `null` |
| 옵션 없음 · 중고 3사 전부 | `null` |

**값이 있다는 것만으로 "가격이 달라진다"를 뜻한다.** 옵션이 있어도 가격이 같으면
`null`이므로, 이 필드를 확인하는 쪽에서 `min`과 `max`를 비교할 필요가 없다.

`price`는 언제나 `price_range.min`과 같다. 검증기가 이 관계를 강제한다.
어긋나면 어느 쪽이 진짜 하한인지 알 수 없어 총 지불액 비교가 무너진다.

품절된 옵션은 살 수 없으므로 범위에서 제외한다.

> 중고 3사는 게시글마다 가격이 하나로 확정되므로 항상 `null`이다.
> 11번가만 값이 생긴다.

### 총 지불액

`price`에는 배송비가 없으므로 총 지불액은 아래처럼 계산한다.

```
총 지불액 = price + delivery_fee.min_fee            # 편의점 픽업 가능한 사용자
총 지불액 = price + delivery_fee.home_delivery_fee  # 픽업이 어려운 사용자
```

거래방식이 여러 개면 경우의 수가 갈리므로, Top-K 단계에서 조합별로 계산한 뒤
최종 순위를 정하는 방식을 쓴다.

**`price_range`가 있으면 총액도 범위가 된다.** 이때 하한만 쓰면 안 된다.
새상품 하한과 중고 확정가를 비교하는 셈이라 결론이 새것 쪽으로 기운다.
어떤 옵션을 고르느냐에 따라 달라진다는 사실을 사용자에게 그대로 알려야 한다.

## 3. 상품 상태 `condition_level`

### 통합 값 6종

| 값 | 의미 |
| --- | --- |
| `NEW` | 새것 |
| `LIKE_NEW` | 거의 새것 |
| `LIGHTLY_USED` | 사용감 적음 |
| `USED` | 중고 (사용감 많음 + 세분화 정보가 없는 경우) |
| `UNSPECIFIED` | 판매자가 상태 등급을 지정하지 않음 |
| `UNKNOWN` | 매핑되지 않는 값이거나 필드 자체가 없음 |

`UNSPECIFIED`(판매자가 안 적음)와 `UNKNOWN`(우리가 매핑 못 함)은 성격이 다르므로 구분한다.

### 플랫폼별 매핑

번개장터와 N플리마켓은 **4등급 체계가 같고 이름만 다르다.** 등급의 위치로 대응시킨다.

```
번개장터    NEW → LIKE_NEW   → LIGHTLY_USED → HEAVILY_USED
N플리마켓   NEW → ALMOST_NEW → USED         → HEAVILY_USED
```

| 플랫폼 | 원본값 | → `condition_level` |
| --- | --- | --- |
| 번개장터 | `NEW` | `NEW` |
| 번개장터 | `LIKE_NEW` | `LIKE_NEW` |
| 번개장터 | `LIGHTLY_USED` | `LIGHTLY_USED` |
| 번개장터 | `HEAVILY_USED` | `USED` |
| 번개장터 | `UNDEFINED` | `UNSPECIFIED` |
| N플리마켓 | `NEW` | `NEW` |
| N플리마켓 | `ALMOST_NEW` | `LIKE_NEW` |
| N플리마켓 | `USED` | `LIGHTLY_USED` |
| N플리마켓 | `HEAVILY_USED` | `USED` |
| 중고나라 | `0` | `NEW` |
| 중고나라 | `1` | `UNSPECIFIED` |
| 중고나라 | `2` | `USED` |
| 11번가 | `새상품` | `NEW` |
| 11번가 | `중고상품` | `USED` |
| 전 플랫폼 | 위에 없는 값 · 필드 누락 | `UNKNOWN` |

> **이름이 엇갈려 보이는 이유** — N플리마켓 원본 `USED`가 통합 `LIGHTLY_USED`가 되고,
> 원본 `HEAVILY_USED`가 통합 `USED`가 된다. 등급 위치로 대응시킨 결과이며 의도된 것이다.

> **`HEAVILY_USED` 통합** — 팀 논의 결과 `USED`로 합쳤다. 그 결과 통합 `USED`에는
> "사용감 많음"과 "중고나라처럼 세분화 정보가 없는 중고"가 함께 들어간다.
> 구분이 필요하면 `condition_raw`를 참조한다(`"HEAVILY_USED"` vs `"2"`).

### 11번가 상태값을 어디서 읽는가

11번가 **검색 API에는 상태 필드가 없다.** `itemCondition`은 표본 50건 전부 `null`이었다.
그래서 새상품 마켓이니 `NEW`로 고정하는 방안을 검토했지만, 실제로 중고가 섞여 있어
폐기했다(`중고 아이폰` 검색 시 `A등급 ... 중고폰 공기계`가 나온다).

상태는 **상품 상세 페이지의 `상품상태` 행**에서 읽는다. 표본 35건 전부 이 행이 있었다.

```html
<th scope='row'>상품상태</th><td>중고상품</td>
```

| 확인한 값 | 건수 |
| --- | --- |
| `새상품` | 31 |
| `중고상품` | 4 |

> **리퍼브는 별도 값이 아니다.** `리퍼 노트북`·`리퍼브 냉장고` 검색 결과도 `새상품`으로
> 나온다. 리퍼브를 구분하려면 다른 근거가 필요하다.

### 11번가 렌털 제외

11번가에는 렌털·구독 상품이 섞여 있고 **`상품상태`가 `새상품`으로 나온다.**
물건은 새것이지만 소유권을 사는 거래가 아니다. 월 구독료가 판매가로 읽히면
총 지불액 비교가 무너지므로 수집 단계에서 제외한다.

판별은 두 단계다.

| 단계 | 근거 | 값 |
| --- | --- | --- |
| 1. 검색 | `unitTxt` | `원/월`, `원~/월` → 렌털 |
| 2. 상세 | `categoryBadge` / `categoryPath` | `렌털` / `렌털/구독 서비스…` → 렌털 |

1단계에서 걸러 상세 요청을 아끼고, 놓친 것을 2단계에서 잡는다.

**검증 49건에서 오탐·누락 0건이었다.**

| 검사 | 표본 | 결과 |
| --- | --- | --- |
| `unitTxt`에 `/월` 있음 → 실제 렌털인가 | 18건 | 18건 모두 렌털 |
| `unitTxt`가 `원` → 렌털이 아닌가 | 31건 | 31건 모두 비렌털 |

제목의 "렌탈" 문자열로 거르면 안 된다. `정수기렌탈가격비교` 같은 검색어 낚시
제목을 단 일반 침대 상품이 대량으로 걸린다. `unitTxt`는 이것을 정확히 구분한다.

`--include-rental`을 주면 렌털도 수집한다. 향후 "빌리는 게 나은가" 판단에 쓸 수 있다.

### 중고나라 상태값을 어디서 읽는가

**JSON-LD의 `offers.itemCondition`은 쓸 수 없다.** 미개봉 상품까지 포함해
표본 22건 전부 `https://schema.org/UsedCondition`으로 고정되어 있다.

실제 값은 상세 페이지 내부 데이터에 따로 있다.

```json
"condition": {
  "productCondition": 0,
  "options": { "fullPackageYn": 0, "limitedEditionYn": 0, "flawedYn": 0 }
}
```

`0`=새상품 / `2`=중고는 화면의 '새상품'·'미개봉' 표기와 대조해 확정했다
(`미개봉` 검색 10건이 10/10 모두 `0` + '새상품' 표기).
`1`은 아직 관측되지 않아 `UNSPECIFIED`로 두고, 실제 값이 발견되면 재확인한다.

### 실제 분포 (표본 40건)

| `condition_level` | 건수 | 플랫폼 |
| --- | --- | --- |
| `LIGHTLY_USED` | 13 | 번개장터 7 · N플리마켓 6 |
| `USED` | 11 | 중고나라 11 |
| `LIKE_NEW` | 7 | 번개장터 3 · N플리마켓 4 |
| `NEW` | 6 | 번개장터 2 · 중고나라 4 |
| `UNSPECIFIED` | 3 | 번개장터 3 |

## 4. 배송비 `delivery_fee`

원본은 `raw`에 그대로 보존하되, 에이전트가 바로 쓸 수 있도록 **부담 주체**와
**대표 금액 두 개**, **정규화된 배송 수단 목록**을 함께 제공한다.

### 구조

```jsonc
{
  "status": "AVAILABLE" | "NOT_AVAILABLE",  // 택배로 받을 수 있는가
  "payer":  "SELLER" | "BUYER" | null,      // 누가 부담하는가
  "min_fee": 2500,                          // 전체 최저 배송비
  "home_delivery_fee": 5000,                // 편의점 픽업이 필요 없는 수단 중 최저
  "options": [ /* 배송 수단별 상세 */ ],
  "raw": { /* 플랫폼 원본 그대로 */ }
}
```

| 필드 | 값 | 설명 |
| --- | --- | --- |
| `status` | `AVAILABLE` \| `NOT_AVAILABLE` | 택배로 받을 수 있는가 |
| `payer` | `SELLER` \| `BUYER` \| `null` | 배송비 부담 주체. 수단마다 다르면 `null` |
| `min_fee` | int \| null | 모든 수단 중 최저 배송비 |
| `home_delivery_fee` | int \| null | 편의점 픽업이 필요 없는 수단 중 최저 |
| `options` | array | 배송 수단별 상세 |
| `raw` | any | 플랫폼 원본 |

### `NOT_AVAILABLE`은 결측이 아니다

**`NOT_AVAILABLE`은 "판매자가 택배를 받지 않는다"는 사실이다.**
"배송비를 알아내지 못했다"가 아니다.

표본 140건에서 `NOT_AVAILABLE`인 28건은 **전부 `trade_method`가 `["MEET"]`** 였다.
직거래 전용으로 올린 글이라 배송 자체가 선택지에 없다.

```
status == NOT_AVAILABLE  →  택배 불가. 직거래로만 살 수 있다
```

이 값을 결측으로 오해해 0원이나 평균값으로 채우면 **배송비 정보가 없는 상품이
"무료배송"이 되어 총액 1위로 올라간다.** 자세한 내용은
[배송비 스코어링 규칙 검토](./배송비_스코어링_규칙_검토.md)를 참고한다.

> 11번가는 `deliveryDescription` 문자열을 해석하지 못해도 `NOT_AVAILABLE`이 된다.
> 표본에서는 한 번도 발생하지 않았지만, 11번가 항목에 이 값이 나오면 그것은
> 진짜 결측이므로 구분해서 봐야 한다.

**`min_fee`와 `home_delivery_fee`를 나눈 이유** — 편의점 택배(반값·알뜰)가 가장 싸지만
주변에 해당 편의점이 없는 사용자에게는 선택지가 아니다. 최저가만으로 비교하면
그런 사용자에게 실제보다 싸 보인다.

`home_delivery_fee`가 `null`이면 **편의점 픽업 외 배송 수단이 없다는 뜻**이다.
픽업이 어려운 사용자에게는 사실상 구매 불가이며, 검증기가 경고로 잡는다.

### `options[]` 항목

| 필드 | 값 | 설명 |
| --- | --- | --- |
| `method` | `FREE` / `STANDARD` / `CONVENIENCE_STORE` / `UNKNOWN` | 정규화된 배송 수단 |
| `carrier` | `GS25` / `CU` / `null` | 택배사. 단정할 수 없으면 `null` |
| `requires_pickup_point` | bool | **편의점 등 픽업 장소 방문이 필요한가** |
| `fee` | int \| null | 배송비(원) |
| `remote_fee` | int \| null | 도서산간 추가 배송비. N플리마켓·11번가만 제공 |
| `raw_code` | any | 플랫폼 원본 코드 |

### 플랫폼별 매핑

| 플랫폼 | 원본 코드 | `method` | `carrier` | `requires_pickup_point` |
| --- | --- | --- | --- | --- |
| 번개장터 | `DEFAULT` | `STANDARD` | — | `false` |
| 번개장터 | `GS_HALF_PRICE` | `CONVENIENCE_STORE` | `GS25` | `true` |
| 번개장터 | `CU_THRIFTY` | `CONVENIENCE_STORE` | `CU` | `true` |
| 중고나라 | `deliveryType: 0` | `STANDARD` | — | `false` |
| 중고나라 | `deliveryType: 1` | `CONVENIENCE_STORE` | `CU` | `true` |
| 중고나라 | `deliveryType: 2` | `CONVENIENCE_STORE` | `GS25` | `true` |
| N플리마켓 | `DIRECT_DELIVERY` | `STANDARD` | — | `false` |
| N플리마켓 | `PICKUP_DELIVERY` | `CONVENIENCE_STORE` | — | `true` |

| 11번가 | `deliveryDescription: "2,500원"` | `STANDARD` | — | `false` |

11번가 도서산간 배송비는 상세 API가 문장으로 준다.

```
제주지역 3,500원, 도서산간지역 6,500원
```

`remote_fee`는 "도서산간 추가 배송비" 하나짜리 필드라 **도서산간 금액만** 넣는다.
제주 금액은 버리지 않고 `delivery_fee.raw.extraCost`에 원문 그대로 남긴다.
제주 사용자에게는 이 값이 과대평가일 수 있다. 표본 20건 중 6건에서 이 안내가 나왔다.

11번가는 오픈마켓이라 편의점 반값택배가 없다. 배송 수단은 일반 택배 하나뿐이고
`무료`면 판매자 부담(`SELLER`), 금액이 표시되면 구매자 부담(`BUYER`)이다.
표본 672건 중 `무료`가 603건으로 대부분이 무료배송이었다.
해석하지 못한 문자열은 0원으로 채우지 않고 `NOT_AVAILABLE`로 둔다.

중고나라 택배사는 세 값이 함께 나온 글에서 확정했다. 화면 표기와 금액이
정확히 대응한다([231559333](https://web.joongna.com/product/231559333)).

| 화면 표기 | 금액 | `deliveryType` |
| --- | --- | --- |
| 일반택배 | 5,000원 | `0` |
| CU 반값택배 | 2,700원 | `1` |
| GS 반값택배 | 2,800원 | `2` |

> N플리마켓 `PICKUP_DELIVERY`는 3,600원 정액이라 플랫폼 픽업 서비스로 판단했다.
> 화면 라벨로 확정하지는 못했다.

### 부담 주체 판정

| 플랫폼 | 판매자 부담(`SELLER`) | 구매자 부담(`BUYER`) |
| --- | --- | --- |
| 번개장터 | `trade.freeShipping == true` | `shippingSpecs.*.fee` |
| 중고나라 | `parcelFee == 1` | `deliveryInfos[].deliveryPrice` |
| N플리마켓 | `payerType == "SELLER"` | `payerType == "BUYER"` |

> **중고나라 `parcelFee`는 금액이 아니라 '배송비 포함 여부' 플래그다.**
> `1`이면 화면에 '배송비 포함·무료배송'으로 표시되고 `deliveryInfos`가 없다.
> `0`이면 `deliveryInfos`에 구매자가 낼 금액이 들어 있다.
>
> **번개장터는 무료배송일 때 `shippingSpecs`를 아예 내려주지 않는다.**
> specs 유무만 보면 무료배송이 '정보 없음'으로 잘못 처리되므로 플래그를 먼저 확인한다.

## 5. 위치 `location`

### 구조

```jsonc
{
  "name": "서창동",                            // 대표 지역명(표시용)
  "full_address": "인천광역시 남동구 서창동",     // 지오코딩 입력용
  "precision": "FULL" | "DONG_ONLY" | "NONE",
  "regions": [ /* 거래 가능 지역 전체 */ ],
  "coordinates": null                          // 지오코딩 단계에서 채움
}
```

| 필드 | 타입 | 설명 |
| --- | --- | --- |
| `name` | str \| null | 대표 지역명. **표시용이다** |
| `full_address` | str \| null | 전체 주소. **지오코딩에는 이 값을 쓴다** |
| `precision` | `FULL` \| `DONG_ONLY` \| `NONE` | 주소 정밀도 |
| `regions` | array | 거래 가능 지역 전체 |
| `coordinates` | null | 지오코딩 단계에서 채운다 |

### `regions[]` 항목

| 필드 | 타입 | 설명 |
| --- | --- | --- |
| `name` | str \| null | 지역명. N플리마켓은 동 이름만 들어온다 |
| `full_address` | str \| null | 전체 주소 |
| `code` | any | 플랫폼 내부 지역코드. **조인에 쓰지 말 것** |

`code`는 N플리마켓의 `rcode`인데 **네이버 자체 코드**라 행안부 법정동코드와 다르다
(표준이라면 강남구가 `1168`인데 여기선 `0968`). 공개 행정구역 데이터와 조인되지 않는다.

**중고 세 플랫폼 모두 좌표를 제공하지 않는다.** 행정동 텍스트만 주므로
거리 계산에는 별도 지오코딩 단계가 필요하다. `coordinates`는 자리만 만들어 뒀다.
11번가는 직거래가 없어 위치 정보 자체가 없다.

### `precision`

| 값 | 의미 |
| --- | --- |
| `FULL` | 시도·시군구·읍면동이 모두 있음 |
| `DONG_ONLY` | 동 이름만 있음. 동명이 전국에 여러 개일 수 있어 지오코딩이 모호함 |
| `NONE` | 위치 정보 없음 |

> **거리 점수를 매길 때 `precision`을 반드시 함께 읽어야 한다.**
> 무시하면 특정 플랫폼이 체계적으로 유리하거나 불리해진다.

### 플랫폼별 원본

| 플랫폼 | 원본 경로 | 형태 |
| --- | --- | --- |
| 번개장터 | `product.geo.address` | 전체 주소 문자열 |
| 중고나라 | `search.locationNames[]` | 전체 주소 문자열 |
| N플리마켓 | `saleProduct.saleProductRegions[]` | **동 이름 + 내부 지역코드** |
| 11번가 | 없음 | 직거래가 없어 `precision: NONE`, `regions: []` |

> 11번가 판매자 주소는 사업자 정보일 뿐 만나는 장소가 아니다. 거리 점수 계산에서
> 제외되어야 하므로 위치를 비워 둔다.

### N플리마켓 주소 보강

N플리마켓 상세 응답은 동 이름만 준다. 계층 주소 필드(`regionName1~3`)가
스키마에는 있으나 값이 전부 `$undefined`다.

함께 오는 `rcode`는 **네이버 자체 코드**로, 행안부 법정동코드가 아니다
(표준이라면 강남구가 `1168`인데 여기선 `0968`). 공개 데이터와 조인되지 않는다.

그래서 크롤러가 네이버 지도의 주소 조회 경로로 전체 주소를 따로 가져온다.

```
GET https://m.map.naver.com/search2/searchAddressById.naver?rcode=11200105
→ 302 Location: ...?query=인천광역시 남동구 서창동
```

`Location` 헤더만 읽으므로 본문을 받지 않는다(건당 약 0.12초). 같은 지역은 캐시한다.
조회 결과는 원본에 `resolvedFullAddress`로 붙고, **하나라도 실패하면 `DONG_ONLY`로 낮춘다.**

### 거리 계산 연동 (카카오맵)

좌표 변환과 사용자-판매자 거리 계산은 **크롤러 밖에서** 한다. 통합 스키마는
주소 텍스트까지 책임지고, 그 뒤는 거리 계산 모듈이 맡는다.
`location.coordinates`는 그 모듈이 채우도록 비워 둔 자리다.

#### 어느 항목을 계산하는가

표본 116건 기준이다.

| `precision` | 건수 | 거래방식 | 거리 계산 |
| --- | ---: | --- | --- |
| `FULL` | 60 | `MEET` 26건 · `PARCEL`+`MEET` 34건 | **필요** |
| `NONE` | 56 | **전부 `PARCEL` 전용** | 불필요 |

**`precision`이 `NONE`인 항목은 예외 없이 택배 전용이었다.** 직거래가 없으니
만날 일이 없고 거리도 의미가 없다. 그러므로 판정 기준은 이렇게 둔다.

```
location.precision == "NONE"  →  거리 계산 건너뛴다 (오류가 아니다)
```

11번가는 **29건 전부** `NONE`이다. 새상품은 언제나 택배로 오므로 정상이다.
**새상품 크롤러는 수정할 것이 없다.** 중고 플랫폼도 택배 전용 글이면 똑같이 `NONE`이라,
플랫폼이 아니라 `precision`으로 분기해야 한다.

#### 어느 필드를 읽는가

**`regions[].full_address`를 쓴다.** `name`을 쓰면 안 된다.
N플리마켓은 `name`에 동 이름만 들어 있어 동명이 전국에 여러 개면 엉뚱한 곳이 나온다.

```jsonc
"location": {
  "name": "영통동",                                  // 표시용. 지오코딩에 쓰지 말 것
  "full_address": "경기도 수원시 영통구 영통동",        // ← 이것
  "precision": "FULL",
  "regions": [ { "name": "영통동", "full_address": "경기도 수원시 영통구 영통동" } ],
  "coordinates": null                                // 거리 모듈이 채운다
}
```

거래 지역이 **여러 개인 항목이 116건 중 7건** 있었다(N플리마켓 최대 3곳).
전부 지오코딩한 뒤 **가장 가까운 곳**을 그 상품의 거리로 삼는다. 첫 번째만 쓰면
판매자에게 불리하게 계산된다.

```
["부산광역시 수영구 남천동", "부산광역시 수영구 민락동", "부산광역시 수영구 광안동"]
```

#### 지오코딩이 실패할 주소

고유 주소 62건을 검사한 결과다. **주소 형식은 3어절 또는 4어절**로 일정하다
(`시도 + 시군구 [+ 구] + 읍면동`).

| 위험 | 건수 | 예시 | 대응 |
| --- | ---: | --- | --- |
| 숫자 붙은 **행정동** | 14 | `화정1동` `양재2동` `개봉제1동` `대연제3동` | 실패 시 숫자·`제` 제거 후 재시도 |
| 시·도 명칭 혼재 | — | `전라북도` / `전북특별자치도` 둘 다 나옴 | 둘 다 받아들여야 함 |
| 존재하지 않는 구 | 1 | `인천광역시 서해구 청라동` (서구가 맞음) | 실패 처리하고 넘어감 |
| 읍·면 | 7 | `경기도 남양주시 오남읍` `충청남도 당진시 송산면` | 정상. 동이 아니어도 유효 |

가장 자주 걸릴 것은 **행정동 이름**이다. 62건 중 14건(23%)이 숫자를 달고 있는데
`화정1동`·`대연제3동`은 행정동이라 법정동 기준 주소 검색에서 안 나올 수 있다
(법정동은 `화정동`·`대연동`).

> 지오코딩에 실패한 항목은 **거리를 0이나 임의값으로 채우지 말고 `null`로 둔다.**
> 0으로 채우면 주소를 못 읽은 상품이 "가장 가까운 상품"이 되어 추천 1위로 올라간다.

### 실제 데이터

**복수 거래 지역 (N플리마켓)** — 판매자가 최대 3곳까지 등록한다

```json
{
  "name": "서창동",
  "full_address": "인천광역시 남동구 서창동",
  "precision": "FULL",
  "regions": [
    { "name": "서창동", "full_address": "인천광역시 남동구 서창동", "code": "11200105" },
    { "name": "구월동", "full_address": "인천광역시 남동구 구월동", "code": "11200101" },
    { "name": "수산동", "full_address": "인천광역시 남동구 수산동", "code": "11200108" }
  ],
  "coordinates": null
}
```

> **거리 점수는 `regions` 중 가장 가까운 지역 기준으로 계산해야 한다.**
> 대표값(`name`·`full_address`)은 첫 번째 항목일 뿐이다.

**동명이인 해소 사례**

| 원본 | 보강 후 |
| --- | --- |
| `중동` | `부산광역시 해운대구 중동` |
| `좌동` | `부산광역시 해운대구 좌동` |
| `당하동` | `인천광역시 검단구 당하동` |
| `용원동` | `경상남도 창원시 진해구 용원동` |

### 실제 분포 (표본 40건)

| `precision` | 건수 | 비고 |
| --- | --- | --- |
| `FULL` | 29 | 번개장터 9 · 중고나라 11 · N플리마켓 9 |
| `NONE` | 11 | 원본에 지역 정보 자체가 없음 |
| `DONG_ONLY` | 0 | 주소 보강으로 해소됨 |

## 6. 거래방식 `trade_method`

`PARCEL`(택배) / `MEET`(직거래)의 배열. 둘 다 가능하면 두 값이 모두 들어간다.

| 플랫폼 | 판정 근거 |
| --- | --- |
| 번개장터 | `trade.freeShipping` 또는 `trade.shippingSpecs` → `PARCEL` / `trade.inPerson` → `MEET` |
| 중고나라 | `tradeType.isPost` → `PARCEL` / `tradeType.isMeet` → `MEET` |
| N플리마켓 | `saleProductDeliveries` → `PARCEL` / `saleProductRegions` → `MEET` |
| 11번가 | 항상 `["PARCEL"]`. 오픈마켓이라 직거래 선택지가 없다 |

중고나라는 플랫폼이 명시한 값을 그대로 읽는다. 다른 두 곳처럼 배송·지역 정보
유무로 유추하는 것이 아니므로 신뢰도가 더 높다.

> 중고나라 `tradeType.isPickup`(편의점 픽업)은 통합 스키마에 대응 값이 없어
> 반영하지 않는다. 표본 15건 전부 `false`였다.

### 실제 분포 (표본 40건)

`MEET`+`PARCEL` 19 · `PARCEL` 11 · `MEET` 10

## 7. 검증 규칙

`validate_unified_schema.py`가 검사하는 항목이다.

**오류(errors)** — 스키마 위반

- 필수 문자열 필드 누락, `platform`·`condition_level`·`trade_method` enum 위반
- `price` 음수, `url`이 `http`로 시작하지 않음
- `delivery_fee.status == AVAILABLE`인데 `raw`가 `null`이거나 `options`가 빈 배열
- `delivery_fee.status == NOT_AVAILABLE`인데 `payer`가 존재
- **`min_fee`·`home_delivery_fee`가 `options`와 불일치**
- `location.precision == FULL`인데 `full_address`가 없는 지역이 존재
- `precision == NONE`인데 `regions`가 존재(또는 그 반대)

**경고(warnings)** — 확인이 필요한 상태

- `status == AVAILABLE`인데 `payer`를 특정하지 못함
- **편의점 픽업 외 배송 수단이 없음**(`home_delivery_fee == null`)
- `coordinates`가 변환 단계에서 채워짐(지오코딩은 별도 단계라는 전제 위반)

## 8. 11번가에서 따로 챙기는 것

11번가는 유일한 새상품 플랫폼이라 수집 방식이 다르다. 중고 3사는 앱 API 하나로
끝나지만 11번가는 **검색 API · 상품 페이지 · 상세 API** 세 곳을 봐야 한다.

| 무엇을 | 어디서 |
| --- | --- |
| 제목 · 가격 · 배송비 | 검색 API |
| 상품상태 · 렌털 판별 | 상품 페이지 HTML |
| 이미지 전체 · 도서산간 배송비 · 옵션 가격 | 상세 API |

### 상세 API에서 더 가져오는 값

상품 페이지가 JS로 부르는 내부 API가 있다. 정적 HTML과 JSON-LD에 없는 값들이 여기 있다.

```
https://www.11st.co.kr/products/v1/pc/products/{상품번호}/detail
```

| 값 | 경로 | 실측 |
| --- | --- | --- |
| 대표 이미지 전체 | `headerImage.images[]` | 평균 1.45장 (JSON-LD는 항상 1장) |
| 도서산간 배송비 | `integDelivery.deliveryInfo.extraCostText` | 20건 중 6건 |
| 옵션별 가격 | `orderTray.optionApiUrl` | 20건 중 3건 |

**옵션 가격이 중요하다.** 검색 결과의 `finalPrc`는 **옵션 중 가장 싼 값**이다.
`maxDiscountInfo.hasOptionPrice`가 `true`인 상품만 골라 9건을 측정한 결과,
**9건 모두 표시가와 옵션 최저가가 일치**했고 최고가는 이만큼 벌어졌다.

| 상품번호 | 표시가 | 옵션 최고가 | 편차 |
| --- | ---: | ---: | ---: |
| 9564934620 | 101,580 | 208,880 | 107,300 |
| 9564798315 | 38,040 | 58,640 | 20,600 |
| 9564905366 | 75,360 | 90,660 | 15,300 |
| 9564873761 | 26,420 | 30,950 | 4,530 |

표시가만 보고 중고와 비교하면 새상품이 실제보다 싸 보인다. 옵션이 있는 상품은
`elevenst.detail.optionPrices`에 `{min, max, count}`로 범위를 담아 둔다.
품절 옵션은 살 수 없으므로 제외한다.

> `optPrcText`(`"~"`)는 화면 표시용 문자열이다. 판별에는 구조화된
> `maxDiscountInfo.hasOptionPrice`를 쓴다. 표본 504건에서 두 값은 예외 없이 일치했다.

### `description`이 비어 있는 이유

11번가 상품 설명은 **판매자가 올린 이미지**다. JSON-LD에 `description` 자체가 없고
정적 HTML에는 상품고시 테이블만 있다. 설명 이미지는 JS가 나중에 불러오므로
우리가 받는 HTML에 들어 있지 않다. 그래서 `description`은 `null`이다.

## 9. 알려진 한계

| 항목 | 내용 |
| --- | --- |
| `coordinates` | 항상 `null`. 거리 계산에는 별도 지오코딩 단계가 필요하다 |
| 11번가 `description` | 항상 `null`. 설명이 판매자가 올린 이미지라 텍스트로 읽을 수 없다 → [8장](#8-11번가에서-따로-챙기는-것) |
| 11번가 이미지 | 갤러리 대표 이미지만 담는다(평균 1.45장). 설명 이미지는 수집하지 못한다 |
| 11번가 옵션 가격 | 상세 API가 실패하면 `price_range`가 비어 표시가만 남는다. 그 경우 옵션 상품인지 알 수 없다 |
| 11번가 도서산간 | `remote_fee`가 단일 필드라 도서산간 금액만 넣는다. 제주 사용자에게는 과대평가일 수 있다 |
| 판매자 신뢰도 | 스키마에 없다. 원본에는 번개장터만 별점·판매건수·가입일이 풍부하고 N플리마켓은 사실상 없어, 그대로 넣으면 플랫폼 간 비교가 불공정해진다 |
| 판매 상태 | 스키마에 없다. 크롤러가 수집 시점에 판매중만 거른다. 캐시가 오래되면 이미 팔린 상품이 남을 수 있다 |
| 등록일시 | 스키마에 없다. `collected_at`은 수집 시각이지 매물 등록 시각이 아니다 |
| 중복 상품 | 제거하지 않는다. 같은 판매자가 같은 상품을 여러 건 올리면 별개 항목이 된다. Top-K 단계에서 별도 툴로 처리한다 |
| 중고나라 `productCondition: 1` | 아직 관측되지 않았다. `UNSPECIFIED`로 두고 있으며 발견 시 재확인이 필요하다 |
| N플리마켓 5번째 상태값 | 등록 화면은 5단계인데 4개만 관측됐다. 미관측 값은 `UNKNOWN`으로 떨어진다 |
| 네이버 지도 주소 조회 | N플리마켓 API가 아닌 별도 경로다. 사이트 변경 시 여기만 깨질 수 있으며, 실패하면 `DONG_ONLY`로 안전하게 낮아진다 |
